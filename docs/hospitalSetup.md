# دليل التشغيل المحلي في المستشفى

## 1. شكل التركيب

خادم داخل المستشفى يعمل طوال الوقت، متصل بسويتش وشبكة Wi-Fi للموظفين. يحتوي PostgreSQL والتطبيق والوكيل HTTPS. أجهزة الاستقبال والصندوق والمستودع وiPad تفتح عنوانًا واحدًا في المتصفح. لا تحتاج تثبيت التطبيق على كل جهاز. لا توجد خدمة سحابية مطلوبة أثناء الاستخدام.

استخدم خادمًا بقرص SSD مشفر، وUPS، ونسخًا على قرص آخر مع نسخة دورية مفصولة. ثبّت عنوان الخادم في DHCP واسمًا داخليًا مثل `nour.hospital.internal`. افصل شبكة الضيوف، ولا تفتح تحويل منافذ من الراوتر إلى الإنترنت.

## 2. التثبيت الأول

جهّز Node.js 24 وPostgreSQL وأدوات `pg_dump/pg_restore` المطابقة لإصدار الخادم وNginx. ثبّت الاعتماديات مسبقًا باستخدام `npm ci`؛ هذا يحتاج الإنترنت أو مستودع حزم داخليًا. تشغيل التطبيق بعد التثبيت لا يحتاج الإنترنت. ثبّت PostgreSQL كخدمة تلقائية، على loopback فقط.

من مجلد المشروع، أنشئ ملفًا مؤقتًا محميًا `.env.setup`:

```dotenv
NOUR_SETUP_DATABASE_URL=postgresql://LOCAL_ADMIN:SECRET@127.0.0.1:5432/postgres
```

نفّذ بالترتيب:

```sh
npm run db:provision
npm run db:generate
npm run db:deploy
npm run db:seed
npm run db:grants
```

ينشئ الإعداد قاعدة `nour_hospital`، وحساب المالك `nour_owner`، وحساب التشغيل المحدود `nour_app`، ومفاتيح عشوائية مختلفة. يرفض إعادة الكتابة فوق إعداد موجود. البذر ينشئ مديرًا فقط، ولا يعيد تعيين حساب موجود أو يضيف بيانات مرضى.

احفظ `.env.migrate` عند مسؤول التحديثات، و`.env.setup` عند مسؤول PostgreSQL، واحصر وصول خدمة الويب في `.env.local` فقط. طبّق ACL مناسبة على Windows؛ قيم صلاحية Unix في السكربت لا تضبط NTFS تلقائيًا.

## 3. العنوان وHTTPS

عدّل `.env.local`:

```dotenv
NOUR_ORIGIN=https://nour.hospital.internal
NOUR_TRUST_PROXY=true
```

أصدر شهادة من سلطة داخلية موثوقة، وثبّت الثقة على جميع الأجهزة، بما فيها iPad. عدّل [مثال Nginx](../deploy/nginx.conf.example) لاسم المنشأة والشبكة ومسارات الشهادات. يبدّل الوكيل X-Real-IP بقيمة اتصال حقيقية، ولا يمرر قيمة العميل كما هي.

الجدار الناري يسمح فقط بـ`443` من شبكة الموظفين. PostgreSQL ومنفذ Next `3000` على loopback. `npm start` يربط `127.0.0.1` عمدًا لأن الوصول من الأجهزة يتم عبر HTTPS والوكيل. لا تستخدم `npm run dev` في الإنتاج. التطبيق يرفض API إنتاجية دون إعداد HTTPS والوكيل الموثوق.

```sh
npm run build
npm start
```

على Linux يمكن استخدام ملف خدمة [nour.service](../deploy/nour.service) كنقطة بداية، بعد تعديل المسارات وحساب الخدمة. فعّل التشغيل التلقائي وإعادة التشغيل عند الفشل. على Windows ثبّت التطبيق كخدمة بحساب محدود بواسطة أداة إدارة الخدمات التي يعتمدها مسؤول المستشفى.

## 4. أول دخول والإعداد

افتح العنوان الداخلي. اسم المستخدم `admin` وكلمة المرور المؤقتة في `.local/firstLogin.txt`. عيّن كلمة شخصية من `12` محرفًا على الأقل، وسجّل الدخول مجددًا، وأضف المفتاح إلى تطبيق TOTP. احفظ وسيلة الاسترداد في مكان محمي ثم احذف ملف كلمة المرور المؤقتة.

من الإعدادات: أضف الأقسام والأجنحة والأسرة، الخدمات والأسعار، ثم حسابًا مستقلًا لكل موظف. أضف المواد من المخزون ثم سجل كميات البداية كحركات موثقة. راجع العملة والأسعار وسياسة المصروف والتحصيل مع المسؤول المالي قبل الاستخدام.

## 5. النسخ الاحتياطي

أنشئ `.env.backup` لدى حساب النسخ الاحتياطي، خارج متناول حساب الويب في التثبيت النهائي:

```dotenv
DATABASE_URL=postgresql://BACKUP_READER:SECRET@127.0.0.1:5432/nour_hospital
NOUR_BACKUP_DIR=/mnt/nour-backups
NOUR_BACKUP_KEY=SEPARATE_64_HEX_CHARACTERS
NOUR_PG_BIN=/usr/lib/postgresql/18/bin
NOUR_RESTORE_TEST_URL=postgresql://RESTORE_OPERATOR:SECRET@127.0.0.1:5432/postgres
```

قارئ النسخ يحتاج SELECT على جميع جداول القاعدة بما فيها `_prisma_migrations` وعلى التسلسلات، وUSAGE على المخطط. حساب التطبيق نفسه لا يملك الوصول إلى جدول الترحيلات؛ استخدم حساب نسخ مستقلًا. مشغّل تجربة الاستعادة يحتاج إنشاء/حذف قواعد الاختبار فقط في بيئة معزولة. يحتفظ مسؤول التشغيل بكلمة مروره، ولا تُعطى لخدمة الويب.

```sh
npm run backup:create
npm run backup:verify -- /mnt/nour-backups/FILE.nourbak
npm run operations:check
```

النسخة لقطة PostgreSQL متسقة، مشفرة أثناء الكتابة، ولا يعتمدها السكربت قبل اكتمالها. يتحقق اختبار الاستعادة من التشفير ويستعيد إلى قاعدة جديدة عشوائية، ويفحص الجداول ثم يحذف قاعدة الاختبار. لا يمس قاعدة التشغيل. علامة نجاح النسخ تختلف عن علامة نجاح الاستعادة.

جدول موصى به كبداية: نسخة كل ساعة، نسخة منفصلة يوميًا، وتجربة استعادة أسبوعيًا. اتفق على أقصى فقد بيانات ووقت استعادة مقبولين؛ النسخ كل ساعة يعني احتمال فقد ساعة من الإدخالات. لا تحذف نسخة قديمة قبل التأكد من وجود نسخ أحدث سليمة، وطبّق سياسة احتفاظ مناسبة للسعة واللوائح. أدوات المشروع لا تحذف أرشيفاتك تلقائيًا.

اضبط المجدول وحالات الفشل والتنبيه فعليًا. مثال cron عند Linux، بعد ضبط المستخدم والمسارات والبيئة:

```cron
0 * * * * cd /opt/nour && /usr/bin/npm run backup:create >> /var/log/nour-backup.log 2>&1
15 2 * * * cd /opt/nour && /usr/bin/npm run security:cleanup >> /var/log/nour-cleanup.log 2>&1
*/5 * * * * cd /opt/nour && /usr/bin/npm run operations:check >> /var/log/nour-health.log 2>&1
```

هذه أمثلة غير مثبتة تلقائيًا. اربط فشل الفحص بإشعار محلي فعلي للمسؤول؛ الملف وحده ليس تنبيهًا. فحص الجاهزية يعتبر النسخ أقدم من `26` ساعة أو تجربة الاستعادة أقدم من `8` أيام فشلًا. إذا اعتمدت نسخًا كل ساعة، اضبط مراقبة التشغيل لتنبه قبل تجاوز هدف الساعة.

احفظ مفتاح النسخ في مكان مستقل وآمن؛ فقدانه يمنع فك النسخ. احتفظ أيضًا بحزمة الإصدار، وإعدادات الشبكة والشهادات. لا تحفظ المفاتيح في المستودع أو على القرص نفسه وحده.

## 6. عند الحاجة للاستعادة

أوقف استقبال الكتابات واحتفظ بنسخة من الحالة الحالية للتحقيق. نفّذ بحساب التشغيل المخوّل:

```sh
npm run backup:restore -- /mnt/nour-backups/FILE.nourbak
```

يستعيد إلى **قاعدة جديدة مولدة** ويطبع اسمها؛ لا يستبدل القاعدة الحية تلقائيًا. يراجع مسؤول PostgreSQL البيانات وملكية الجداول وصلاحيات المالك و`nour_app`، ويلغي جلسات الدخول المستعادة، ويطبّق الترحيلات اللازمة إن كانت النسخة أقدم، ويجري اختبار قبول. بعدها فقط يغيّر `DATABASE_URL` و`MIGRATION_DATABASE_URL` إلى القاعدة المستعادة ويعيد تشغيل الخدمة. لا تستخدم حساب مشغّل الاستعادة لتشغيل التطبيق، ولا تحول المؤشر قبل مراجعة الصلاحيات. وثّق العملية والنسخة المستخدمة والفترة المفقودة.

## 7. اختبار قبول قبل التشغيل

استخدم تثبيتًا تجريبيًا منفصلًا. من جهازين: سجل مريضًا، حاول حجز السرير نفسه، انقل المريض، أضف خدمة ومادة، راقب الخصم، سجّل دفعة جزئية ثم سدد وغادر، وراجع ظهور التحديث على الجهاز الثاني. اختبر دور المستودع ومنعه من قراءة المرضى. افصل الشبكة وتأكد من ظهور التنبيه، ثم أعد الاتصال وراجع عدم تكرار الدفع. اطبع إيصالًا بالعربية، واختبر النسخ والاستعادة على جهاز بديل وتوقف الكهرباء الآمن.

نفّذ `npm run operations:check`، واختبر الثقة بالشهادة والجدار الناري والنسخ الخارجية يدويًا. نجاح البناء وحده لا يكفي لاعتماد المستشفى. وثّق موافقة المسؤول الطبي والمالي وإجراءات الطوارئ والحدود المذكورة في دليل الأمان.

## قاعدة التطوير الحالية على Windows

قاعدة المشروع الحالية مستقلة على `127.0.0.1:5544`، والبيانات في `.local/postgres`. استُخدمت أدوات PostgreSQL الموجودة أصلًا على الجهاز، دون تغيير قاعدة المشروع السابق. بعد إعادة التشغيل يمكن تشغيلها من PowerShell داخل مجلد المشروع:

```powershell
& '..\sham-his\node_modules\@embedded-postgres\windows-x64\native\bin\pg_ctl.exe' -D '.local\postgres' -l '.local\postgres.log' -o '-h 127.0.0.1 -p 5544' start
npm run dev
```

هذا المسار خاص بجهاز التطوير. في المستشفى ثبّت PostgreSQL كخدمة مستقلة ولا تعتمد على `node_modules` لمشروع آخر. إعدادات التطوير تستخدم HTTP على `localhost` فقط؛ لا تستخدم بيانات مرضى فعلية فيها.
